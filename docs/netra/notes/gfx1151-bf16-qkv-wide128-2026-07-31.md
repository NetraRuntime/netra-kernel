# gfx1151 BF16 QKV wide-load decode — 2026-07-31

All results in this note are for AMD Ryzen AI Max+ PRO 395, `gfx1151`.
GPU claims are measured with HIP events or rocprofv3. Serving claims are measured
with streaming host wall time. Derived values are labeled explicitly.

## Decision

Accept `bf16_qkv_decode_wave1_wide128_gfx1151.s` for the exact Qwen3.6
full-attention M=1 BF16 QKV projection, N=9216 and K=2048. It replaces the
accepted raw wave1 implementation without changing the 24-byte, 8-byte-aligned
three-pointer kernarg ABI, grid `(1152,1,1)`, workgroup 256, caller HIP stream,
graph-pool pointers, or checkpoint weights.

The candidate keeps one output row per wave32 and replaces scalar
`global_load_b32` operand traffic with `global_load_b128`. Each lane executes
eight K-loop iterations with four BF16 dot2 operations per iteration instead of
thirty-two scalar-load iterations. Final compute remains hand-written raw
AMDGCN assembly for gfx1151. HIP C++ is used only for launch, graph validation,
and timing.

| gfx1151 code object | SHA-256 | status |
|---|---|---|
| baseline wave1 | `0d700a1d29739041d9b0e475b7be33edf2c05a22a354a73358747b8f934cdd67` | measured |
| candidate wide128 | `aae22ff0fc0649273ab69a65c36fff2ad7157fd1a89571ebc1da82b6481bcf69` | measured |

Both code objects have zero LDS and zero scratch. Metadata preserves wave32,
24-byte kernarg size/alignment, and max workgroup 256. Source metadata changes
VGPR count from 18 to 22; rocprofv3 reports the same 24-VGPR and 128-SGPR
allocation granules for both.

## Correctness

The production validator used real checkpoint weights from all ten
full-attention layers at exact M1/N9216/K2048. Against model-native rocBLAS BF16
GEMM, the candidate maximum absolute BF16 difference was 0.015625 and at most
17 BF16 elements differed in a layer.

FP64 spot checks on real layers 3, 27, and 39 gave the same maximum errors as
rocBLAS and slightly lower candidate mean error. The candidate was closer to
FP64 at 17, 14, and 8 elements respectively, while rocBLAS was closer at zero.
This is an appropriate high-precision validation; it does not imply arbitrary
accumulation orders are bit-exact.

Five matched synthetic greedy requests produced deterministic candidate output
but diverged from the old wave1 sequence because the legal BF16 accumulation
order changed. Candidate eager versus full graph was 5/5 output-hash exact. A
natural Rayleigh-scattering prompt remained coherent and its first 128 greedy
tokens were identical to the old kernel and to three candidate repeats, hash
`be4a789bd20721c8573aded6af1de30c0a118b3ec4e73427f3be4a66300838e2`.

## HIP-event timing

A matched isolated raw-wave1/wide128 interleaved sweep used the identical exact
shape and launch geometry:

| gfx1151 measured raw ASM | median kernel time | relative |
|---|---:|---:|
| accepted wave1 | 0.293974 ms | 1.000x |
| accepted wide128 | 0.253694 ms | 1.15878x |

The production validator measured ten real layers at 2.635738 ms median and
2.697101 ms p90 for wide128. The model-native rocBLAS baseline was 5.874047 ms
median, so wide128 was 2.22862x faster in that separate A/B. Graph replay of the
ten-layer candidate pass was 2.625960 ms median and 2.688862 ms p90.

## Matched serving A/B

Five matched seeds used exact 1 input + 128 output, cached tokens 0, eager graph
disabled, and dFlash disabled. Decode wall covers 127 timed output intervals.

| gfx1151 measured median | old QKV + shared wide128 | QKV wide128 + shared wide128 | change |
|---|---:|---:|---:|
| decode wall | 3253.504 ms | 3208.769 ms | -1.375% |
| output throughput | 39.035 tok/s | 39.579 tok/s | +1.394% |
| E2E wall | 3314.631 ms | 3266.017 ms | -1.467% |

The newest accepted non-speculative batch-1 result is therefore 39.579 tok/s
on gfx1151, measured. The 50 tok/s target is not yet achieved.

## Full graph gate

Native SGLang full decode graph captured batch 1 in 1.38 s and reported 0.07 GB
incremental graph memory. Candidate eager and graph output hashes matched 5/5.

| gfx1151 measured median | candidate eager | candidate full graph |
|---|---:|---:|
| decode wall | 3208.769 ms | 3231.249 ms |
| output throughput | 39.579 tok/s | 39.304 tok/s |
| E2E wall | 3266.017 ms | 3278.935 ms |

Full graph is 0.701% slower in decode wall and 0.696% lower in output throughput,
so eager remains the batch-1 performance choice. Graph remains correctness-safe.

## Negative LM-head wide-load experiment

The current LM head is still the largest individual decode kernel: 159.333 ms
across 32 calls, or 20.452% of summed kernel time in the newest request trace.
The same wide-load idea was tested separately and rejected.

| gfx1151 measured LM-head raw ASM | median | change vs accepted |
|---|---:|---:|
| accepted b32-load wave1/WG64 | 4.99115 ms | baseline |
| experimental b64 loads | 5.07370 ms | +1.654% |
| experimental b128 loads | 5.07763 ms | +1.733% |

The LM-head experiments retained the same shape and launch geometry but regressed,
consistent with this 992.5 MiB projection being bandwidth dominated and already
well scheduled. The experimental source files are not shipped.

## SGLang versus llama.cpp interpretation

No same-checkpoint llama.cpp A/B exists yet, so no framework ratio is claimed.
The newest gfx1151 trace shows that SGLang's scheduler/dispatch layer is material
but not the dominant measured bottleneck: 89.372% of wall is summed GPU work,
while positive launch gaps occupy 11.139%. It dispatches about 981 GPU kernels
per forward step and performs one result event synchronization per output step.

The result synchronization is part of SGLang's overlap schedule and can overlap
the next forward pass; deleting it blindly is not valid. Even an estimated
zero-overhead lower bound from 779.047 ms of GPU work over 32 forward steps is
about 24.35 ms/step, or only about 41.1 tok/s. Thus a llama.cpp advantage cannot
be explained by Python scheduling alone: matching it requires both a tighter,
less fragmented execution path and additional kernel/fusion gains. The 41.1
tok/s figure is derived, not measured serving throughput.
